## Scope and evidence

This audit covers the independent `swyp-lang` product module in the Nexus
workspace. Existing modified and untracked implementation work was preserved.
No source reset, Git clean, staging, commit, push or remote publication occurred.
The coordinated audit branch is `codex/nexus-audit-2026-09-30`.

The readable, non-ignored text inventory is recorded in
[`2026-09-30-inventory.tsv`](2026-09-30-inventory.tsv), including each file's
line count, byte count and SHA-256. The final inventory reads 355 files and
79,243 lines after the last loader regression below. Inventory
and compilation cover the whole readable product. Detailed semantic inspection
focused on the frontend, JSON/IR validation, effects, interpreter preparation,
contracts/synthesis, HIR linking/ownership/lowering, module loading, compiler
publication, cache boundaries and native calling conventions. This is a
risk-based engineering audit, not a proof that every line is defect-free.

Secrets, ignored model weights, private/user data and old generated binaries
were excluded. Tests build and execute their own temporary artifacts. Prior
versions of edited existing files were retained under the local temporary
`nexus-swyp-audit-20260930` directory. Generated validation/build artifacts stay
outside tracked source or in the already ignored `agent-lab`/`bin` directories.

## Architecture findings and remaining limits

Swyp remains independently buildable and deterministic without Ilaria. The
optional model client, generator-facing judge and declarative DTO generation
integrate through text/schema/protocol surfaces instead of importing Ilaria or
SwypikOS internal packages. Prepared Core executables own snapshots, strict IR
validation checks effect/capability propagation, and pure execution rejects
effectful entries before guest instructions run. Contract success distinguishes
finite exhaustive execution from sampling and unsupported/unknown cases.

The HIR work is substantial and was preserved: explicit-root module graphs,
qualified direct-use linking, nominal/value types, fixed layout, descriptor
plans, conservative ownership/borrow checks and lowering to the existing Core
IR rather than a duplicate runtime. Many richer HIR types remain unsupported
by particular execution backends; a language-manifest type list is not a claim
that every type executes on every backend.

Material limitations remain:

- General resumable effects and the scoped SwypikOS capability broker are not
  connected to Core execution. Native `-allow-*` switches grant broad build-time
  authority and do not provide scoped capability tokens, attenuation, broker
  evidence or sandbox isolation.
- Native process execution remains policy-dependent and fail closed. Plaintext
  IPv4 fetch/connect support is not a general DNS/TLS HTTP client.
- The C AOT backend supports its pure scalar subset; descriptor/storage-backed
  HIR programs require other supported paths. Rich type support remains partial.
- Native storage arenas are bounded and bump allocated, with 64 descriptor
  slots and no payload reuse. Core storage uses different, explicit reference
  budgets. Success/failure parity needs resource-budget contracts, especially
  for long-lived programs and repeated vector growth.
- Cache lookup trusts a local cached executable at its content-derived name;
  no signed provenance or artifact checksum sidecar is checked on restoration.
  Compiler executable identity is hashed, but transitive linker/toolchain inputs
  and native CPU features are not a complete reproducible-build attestation.
- Module root symlink checks and dependency hash rechecks are useful but are
  not an OS-level race-free filesystem sandbox against hostile concurrent path
  replacement. The source loader must run with host authority appropriate to
  the selected explicit tree.
- Finite contracts, static checks and fuzz smoke do not prove the complete
  language, optimizer or machine-code backends correct. Native ARM64 structural
  checks/cross-builds do not establish runtime parity on real ARM64 hardware.
  Some Windows GCC-assisted DLL/mixed-FP execution cases remain skipped locally;
  a passing Linux suite does not execute those Windows-only calling paths.
- Historical measurements and documents contain earlier product paths and
  status snapshots. They are retained as history; broad claims of world-leading
  performance or full self-hosting are not supported by this audit.

## Priorities for a stronger system

1. **Correctness and authority first:** specify resumable EffectRequest/Result
   semantics with SwypikOS-scoped grants, lease/fence binding, explicit error
   states and effect evidence. Keep the implementation in the owning product.
2. **Backend evidence:** differential property testing across safe Core, fast,
   turbo, x64 and ARM64 for values, traps, aliasing/ownership and documented
   resource profiles; run generated ARM64 images under a controlled emulator
   and on native hardware. Preserve minimized regression cases.
3. **Resource/runtime completion:** declarative budgets shared by lowering and
   each runtime; define safe allocation reuse without stale descriptor reuse,
   deterministic failure and scope destruction for supported aggregates.
4. **One semantic frontend:** converge executable/Core/component parsing on the
   typed HIR incrementally; keep explicit supported-backend/type matrices and
   stable diagnostics instead of widening claims before execution exists.
5. **Build provenance:** artifact checksums, manifest/compiler/toolchain identity,
   target CPU feature binding and reproducible native output checks; fail closed
   or rebuild when cached evidence is invalid.
6. **Useful competitive targets:** select real compute/verifier workloads and
   publish reproducible correctness-gated latency, throughput, allocations,
   artifact size and reliability measurements against documented baselines.
   Progress should be measured per workload and release, not by absolute claims.
