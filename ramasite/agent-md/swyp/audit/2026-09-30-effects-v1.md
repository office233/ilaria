# Swyp broker execution milestone — 2026-09-30

## Scope and preservation

This milestone extends the existing safe Core interpreter. It does not add a VM,
a capability broker, a model dependency or an ambient host-effect provider.
The shared schema, generated DTOs and protocol validation are maintained by the
workspace integration owner. Existing dirty work was preserved on the dedicated
`codex/nexus-effects-v1` branch. Pre-edit Swyp source/docs were copied to
`%TEMP%/nexus-swyp-effects-v1-20260930-204817`.

## Actual supported behavior and limits

The handler-backed safe interpreter supports `clock.read` and read-only `fs.read`
plus all existing pure Core operations and calls. Core's clock type remains u64;
wire clock results are canonical nonnegative i64 Unix milliseconds converted
exactly. File data is opaque owned bytes, including arbitrary binary data; path
conversion to wire requires bounded UTF-8 and no NUL.

Pure Run/Fast/Turbo and contract verification retain their prior pure-only
boundary. Other effects, native broker transport, general user effect syntax,
write/process/network effects and externally serializable continuation snapshots
are not implemented. Unsupported transitive declared effects fail before guest
execution. Multiple requirements propagated from separate callees are permitted;
an actual instruction with an ambiguous requirement fails preflight.

The host owns grants, task/lease/fence validation, path confinement, signed
receipts and retry/recovery decisions. Swyp checks typed correlation, not host
receipt signatures. No handler means no effectful execution. Cancellation cannot
resume after a handler returns, but an embedding handler must itself respect its
context. The CLI returns on a blocked stdin deadline; embedding callers must
close a blocked reader to release its pending goroutine. CLI deadlines begin
after compiler input reading/lowering/preparation. This adapter is not an OS
sandbox.

Next useful work is explicit instruction requirement binding for multiple same-
effect grants in one function, host-budget propagation, brokered write/network
operations with recovery semantics, and continuation snapshots only if a real
scheduler requirement warrants them. These should extend this existing machine
and protocol rather than introduce a parallel runtime.
